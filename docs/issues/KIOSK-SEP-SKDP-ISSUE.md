# Description

On the BPJS reference (Rujukan) path of kiosk self-registration, SEP creation
fails: the request to `POST /sep` is rejected with HTTP 400 and the body
`{"status":"Bad Request","code":"400","data":"Invalid string date"}`.

The SEP payload generated by the kiosk sends the `sepDate` field as a date-only
string (`"2026-02-11"`), while the receiving VClaim `POST /sep` contract expects
a value that carries a time component as well.

Because SEP creation fails, registration cannot be completed on this path and no
receipt is printed. The affected capability is the kiosk BPJS self-registration
SEP/SKDP integration, delivered under IMPLEMENTATION-PLAN
`c013-kiosk-queue-display-web/docs/plans/KIOSK-SEP-SKDP-IMPLEMENTATION-PLAN.md`
(status COMPLETED) and ARCHITECTURE
`c013-kiosk-queue-display-web/docs/architecture/KIOSK-SEP-SKDP-ARCHITECTURE.md`.

This ISSUE captures the reported problem only. It does not identify the cause,
select a correction, or define how the correction will be realized.

# Desired Outcome

A patient registering through the kiosk with a BPJS Rujukan reference obtains a
completed registration: SEP creation succeeds against the VClaim `POST /sep`
contract, the kiosk prints the normal registration receipt including the SEP
number, and the admisi-fallback notice is not shown.

# Current Situation

- Registration on the Rujukan reference path stops at SEP creation with HTTP
  400 `Invalid string date`; the normal receipt is not printed.
- The generated payload contains `sepDate: "2026-02-11"` — a date-only value
  with no time part.
- The same payload builder is used by both the Rujukan and the SKDP reference
  paths, so the SKDP path is expected to be affected as well. This expectation
  is unconfirmed: TC-BR-03, which would capture the SKDP SEP payload, is
  BLOCKED for an unrelated data reason (see Notes).
- The admisi fallback behaved correctly in the presence of this failure
  (TC-ERR-01 PASS): exactly one `POST /sep` attempt was made, the existing
  registration was preserved, and both notice lines printed. This ISSUE does not
  concern the fallback behavior.
- The non-BPJS (no-reference) registration path is unaffected (TC-RE-01 PASS).

# Notes

## Open question for BUG-INVESTIGATION

The tester's stated expectation in TEST-EXECUTION is the format
`yyyy-mm-dd hh:mm`. The receiving contract code cites the enum member
`DateFormatEnum.YMD_HMS`, whose name suggests a seconds component as well. The
exact string pattern the endpoint accepts has not been established at intake.
This ISSUE therefore states the business outcome (SEP creation must succeed and
the normal receipt must print) and does not fix a target format string.
Resolving the accepted pattern is BUG-INVESTIGATION work.

## Not raised as an ISSUE

The tester also reported that TC-BR-02 and TC-BR-03 are BLOCKED because the dev
database is older than the kiosk business date, leaving no active SKDP
participant, and that a data owner would need to refresh SKDP dev data from a
backup. The tester explicitly recorded this as **not a product defect**, and
TEST-EXECUTION §3 lists DEF-001 as the only open issue. It is therefore not
captured as an ISSUE here. It is recorded only so that TC-BR-02, TC-BR-03,
TC-HP-02, and TC-HP-03 remain executable in a later test session once the data
is available.

## Scope boundary

This ISSUE is solution-neutral. It does not determine the cause of the

receiving contract, define any correction, or define how it will be tested.
